sarcina · one plugin, one day

A Day as demo.nvim

I am a plugin loaded by sarcina. This is what happens to me over four launches, seen from three sides: the code that acts on me, the stages I move through, and the text sarcina prints about it.

Every log block is copied from a real headless run against two local git repos in a throwaway directory. Durations and hashes are from that run. The panel text was read from the panel buffer; in a live session it opens after 250 ms or when something fails.

Show
before launch

Written into a spec

I am a lazy plugin. I have a command and a key, so I wait to be used. I also carry a dependency, a shell build and some options.

Code

-- lua/plugins/demo.lua
return {
  {
    '/…/repos/demo.nvim',
    deps = { { '/…/repos/util.nvim' } },       -- an inline spec
    build = 'sleep 0.3 && echo compiled > built.txt',
    cmd = 'Demo',
    keys = { { '<leader>d', '<cmd>Demo<cr>', desc = 'Run the demo' } },
    opts = { greeting = 'hello' },
  },
}

manifest.load reads my spec file once and expands the { 'path' } shorthand into repo. The resolver derives my name from the repo path, lifts util.nvim out of my deps and rewrites deps to plain names, sorts dependencies first, sets my triggers from cmd and keys, and generates my tasks.

Lifecycle

I have cmd and keys, so I am lazy. My task list is three entries long.

  • install git_clone
  • build shell, once per commit
  • load_trigger holds rtp, load, keys

Log

These four lines go only to ui.on('debug') listeners. They never become toasts.

09:00

First launch, cold

Nothing of me exists on disk yet.

Code

My build task is { type = 'shell', per_commit = true }. The wrapper in executors.lua runs git rev-parse HEAD and compares it with .git/sarcina-build before it runs anything.

Lifecycle

  1. setup() returns at once. The tasks run in the background.
  2. I cannot start until util.nvim has finished, because I depend on it.
  3. git_clone clones me into a staging directory, then renames it to stdpath('data')/sarcina/plugins/demo.nvim.
  4. The shell build runs in my directory.
  5. It succeeds, so my commit hash is written to .git/sarcina-build.
  6. load_trigger arms two stubs: the :Demo command and the <leader>d key.
  7. I am not on the runtimepath yet.

Log

Toasts: none. A clean setup() is silent.

09:05

Someone types :Demo

The stub I left behind gets used.

Code

scheduler.load does the claiming. The keymaps task defines my real mapping, which is why <leader>d survives losing its stub: sarcina owns the rhs.

Lifecycle

  1. The :Demo stub fires.
  2. The scheduler claims me and any dependency still waiting.
  3. It removes every stub, so my other trigger cannot start a second load.
  4. It appends rtp, load and keys to the current task list.
  5. When the load succeeds, it replays the command.

Log

Toasts: none. A successful lazy load stays quiet. Afterwards <leader>d maps to <cmd>Demo<cr> with the description "Run the demo".

13:00

Second launch, warm

Nothing needs doing, and the log says so.

Code

No new code runs. The install task sees my directory and reports already installed. The per-commit gate sees that HEAD equals the recorded hash and reports up to date.

Lifecycle

  1. install finds my directory and clones nothing.
  2. build finds that HEAD matches .git/sarcina-build and is skipped.
  3. load_trigger arms the stubs again.
  4. I stay off the runtimepath until someone uses :Demo or <leader>d.

Log

Toasts: none. The run is too fast for the panel to open on its own.

18:00

A bad evening

Someone pulls a new commit, and my build breaks.

Code

The same per-commit wrapper runs, but this time the comparison fails, so the build executes. When a task fails, the runner in tasks.lua marks the rest of that plugin's tasks as skipped.

Lifecycle

  1. HEAD no longer matches the recorded hash, so the build runs again.
  2. It fails.
  3. My remaining task is skipped with the note build failed.
  4. load_trigger never runs, so I arm no stubs. :Demo and <leader>d do not exist this session, and I am not on the runtimepath.
  5. The run ends with one error toast. The panel opens and stays open.

Log

ERROR [Sarcina] 3 done, 1 failed, 1 skipped

On the next launch the build ran again and failed with the same panel. The record still held d4b8d94… while HEAD was 5495c54…, so a failed build is retried until it succeeds.

What running it showed

A failed build takes the whole plugin out of the session. build comes before load_trigger in my task list, so when it fails I arm no stubs, and the key and the command vanish instead of printing an error when used. That follows from the rule that a failure skips the rest of a plugin's tasks. Arming the stubs first and reporting the failure on first use would be a small change to the task order.
